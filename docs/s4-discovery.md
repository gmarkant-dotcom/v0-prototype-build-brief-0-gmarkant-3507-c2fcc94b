# S4 Phase 0 Discovery

Read-only mapping done before any code was written, ahead of S4-M (migrations) and S4-1 (Phase 1 build). Read `docs/ligament-design-language.md` first per instruction.

## 1. RFP Broadcast wizard

Lives entirely in `app/agency/page.tsx` (2,700+ lines, single file - `AgencyRFPContent`, default-exported wrapped as `AgencyRFPPage`). Step-based, not file-per-step: a `currentStep` number state (1-5ish) gates which JSX block renders, all in one component. State model is one big `masterRfp` object (`MasterProject`-shaped) held in `useState`, mutated via small `update*` handler functions (`updateRequiredDesignation`, `updateRequiredInsurance`, `updateRequiredCoi`, `updateRequiredNotes`, etc. for business criteria alone). No separate wizard-state library or reducer - plain `setMasterRfp(prev => ({...prev, ...}))` throughout.

Business criteria requirements are defined/edited in one step's JSX (`app/agency/page.tsx` ~line 1895 pre-S4-1, "Business criteria" `GlassCard`): a checkbox per `DESIGNATION_KEYS` entry and per `INSURANCE_KEYS` entry (both from `lib/business-criteria.ts`), writing into `masterRfp.business_criteria_required`, which is `BusinessCriteriaRequired` shaped (`{ designations, insurance, notes }`).

Persistence: the wizard's `business_criteria_required` travels inside `master_rfp_json` (a JSONB blob) when broadcasting to existing pool partners (`app/api/agency/broadcast-rfp/route.ts`, written into `partner_rfp_inbox.master_rfp_json`), and as its own top-level `business_criteria_required` JSONB column on `rfp_magic_tokens` for the separate Lightning RFP Magic Link flow (`app/agency/magic-rfp/page.tsx` -> `app/api/agency/rfp/magic-link/route.ts`). Two different storage locations for the same conceptual data, per the two broadcast flows - this pattern already existed before S4 (mirrors `require_terms_disclosure` from migration 070) and S4-1's requirement-tier priority data follows it: no new column added, priority lives as new keys inside these same two existing JSONB locations (see migration 071's comments for the full reasoning).

## 2. Bid form: portal vs. guest

**Portal:** `app/partner/rfps/[id]/page.tsx` (~2,050 lines). **Guest:** `app/rfp/respond/[token]/page.tsx` (~1,150 lines). Two separate files, two separate component trees - no shared bid-form component existed before S4-1. Both independently: fetch RFP data, hold local form state (`businessCriteriaResponses`, proposal/budget/timeline fields, terms disclosure), and POST on submit.

Business criteria confirmations render today as a single flat list (no tiering) in both: a designation checkbox block, an insurance checkbox block, a COI checkbox - each ungated by priority, all effectively "required" in the sense that `compareBusinessCriteria` (the existing gap-report function) flags any unmet gated item without distinction. This is the "implicit required" behavior S4-1's pre-migration fallback had to preserve exactly. The guest page additionally renders a second, read-only, non-interactive preview of the same requirement list further up the page (a dark-theme summary card, separate from the actual editable form) - left untouched by S4-1 since it only ever lists labels, no priority-specific logic to break.

Persistence: both paths submit to a JSON POST body containing `business_criteria_responses` (the vendor's holds, `BusinessCriteriaHolds` shaped) alongside proposal/budget/timeline/terms/attachments. Portal posts to `/api/partner/rfps/[id]/response`; guest posts to `/api/rfp/guest/[token]`. **Both write to the same `partner_rfp_responses` table** - guest bids are not a separate table, just nullable `inbox_item_id`/`partner_id` on the same row (confirmed via migration 057's history in `LIGAMENT_CONTEXT.md`). This is why one new column (071) and one shared write-guard pattern cover both paths.

**Genuine gap found:** neither path prefilled business criteria confirmations from the vendor's saved profile before S4-1 - every bid started from a blank `BusinessCriteriaHolds` unless the vendor had already bid on this exact RFP before. The spec's "prefill from profile" requirement was not a refinement of existing behavior, it was new. Implemented in S4-1 for the portal path only (guest has no profile, per spec) via a direct `profiles.business_criteria` fetch when no prior response exists on this RFP.

## 3. Schema

- `business_criteria_required` (JSONB): on `rfp_magic_tokens` as a real column, and nested inside `partner_rfp_inbox.master_rfp_json` for the wizard flow. Shape: `{ designations: Partial<Record<DesignationKey, true>>, insurance: Partial<Record<InsuranceKey, InsuranceRequirement>> & { coi_on_file?: boolean }, notes: string }` (`lib/business-criteria.ts`).
- `business_criteria_responses` (JSONB): on `partner_rfp_responses`. Shape: `BusinessCriteriaHolds` (designations with holds/certifying_body/certification_number/self_certified, insurance with has_coverage/limit, company_facts).
- `partner_rfp_responses` is the one bids table for both portal and guest paths (see #2).
- Migration convention: numbered files in `supabase/migrations/`, `NNN_snake_case_description.sql`, comment header explaining the "why," `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` for additive changes, a verification `SELECT` at the end (070's is left live/uncommented; S4's own two files comment theirs out per this run's explicit instruction). Latest applied: **070** (`070_terms_disclosure.sql`, terms alignment). No `048_*.sql` file exists on disk despite a row for it in `LIGAMENT_CONTEXT.md`'s migration log - a known, pre-existing gap unrelated to S4, not introduced by this run.

## 4. Profile prefill sources

`profiles.business_criteria` (JSONB, same `BusinessCriteriaHolds` shape used everywhere else) is the vendor's own saved designations/insurance/COI holds, edited on `/partner/legal`. This is the only clean prefill source that maps 1:1 to what the bid form asks for - same shape, same keys, zero translation needed. Used in S4-1's portal-path prefill.

No other criterion type has a clean profile-side source. Scope requirements beyond business criteria (the spec's "and scope requirement on an RFP" language) have no dedicated vendor-side "I have this capability" record anywhere in the schema today - there is nothing to prefill from, and S4-1 does not invent one. Terms disclosure already has its own, separate prefill mechanism (`profiles.default_terms`, migration 070) - not touched by S4-1, no overlap with business criteria.

## 5. Compare view / bid detail consumption

`components/bid-compare-view.tsx` renders a side-by-side `<Table>` of bids, one `<TableRow>` per data dimension (Score, Budget, Timeline, Terms, Business Criteria, Attachments...) and one `<TableCell>` per bid in that row. `components/bid-detail-sheet.tsx` renders one bid's full detail in a sheet with tabs (Analysis / Cost Breakdown / Evaluate). Both already import `compareBusinessCriteria` from `lib/business-criteria.ts` and render a legacy, presence-based gap summary (no priority tiers) - left untouched by S4-1.

The new compliance matrix slots in as: a new `<TableRow>` in `bid-compare-view.tsx`, inserted immediately before the existing "Score" row (`<TableBody>`'s first row) - literally "before scoring" per spec. In `bid-detail-sheet.tsx`, a new block at the very top of the "Analysis" tab (before "AI Analysis"), ahead of the separate "Evaluate" tab where subjective scoring happens. Both are gated on `computeRequirementCompliance(...).hasTierData` - render nothing for any RFP without explicit priority data, never a fabricated pass.

Both read `row.business_criteria_acknowledgments` for cannot-meet reasons - **this field is not yet in either surface's Supabase `.select()` column list** (both use explicit column lists, not `select("*")`), so cannot-meet reason text will not appear in compare/detail view until a follow-up adds it there. Met/unmet status itself, and the matrix's pass/fail count, work today regardless (computed from `business_criteria_required` + `business_criteria_responses`, both already selected). Flagged as a spec follow-up in the final report, not silently skipped.

## 6. Type system

**Hand-rolled, not generated.** No `database.types.ts` or Supabase CLI-generated types file exists anywhere in the repo (confirmed by search). Every file defines its own inline TypeScript types/interfaces for Supabase query results (`type ResponseRow = {...}`, `type BidRow = {...}`, etc.), and Supabase client calls are typed loosely (query builders resolve to broad/`any`-adjacent shapes in several places, e.g. the `saved` variable in both response API routes needed an explicit type annotation to satisfy strict null checks after this run's write-guard refactor). This determined the S4-1 typing approach directly: **new fields are added as optional properties on existing hand-rolled types** (`business_criteria_acknowledgments?: unknown` on `ResponseRow`/`BidRow`, always read through a `normalize*` function that treats `undefined` identically to "not present yet"), no regeneration step needed or possible.

## 7. Spec contradictions / material difficulties flagged (not silently adapted)

- **"Priority column on the criteria/requirements structure"** assumes normalized criterion rows. The actual schema stores criteria as a fixed, code-defined key set inside JSONB blobs (see #3), with no per-criterion row to add a column to, and no reliable way to blind-backfill nested JSONB from a generic migration. Resolution (see migration 071's own header comment for the full reasoning): priority is added as new JSONB keys at the application layer instead of a SQL column; the migration's real, needed work is the cannot-meet acknowledgment column instead. This is a genuine, material deviation from the literal spec text, made and documented rather than guessed silently.
- **"Backfill existing rows to 'preferred' so current RFPs are unaffected"** - same root cause. No SQL backfill is performed (see above). Instead, RFPs with zero explicit priority data are detected via `hasExplicitPriorityData()` and rendered with the pre-S4-1, untiered UI unchanged - functionally achieves "current RFPs are unaffected" (no fake required/preferred split, no new red flags on old data) without a backfill statement, but does not literally set a stored value to `'preferred'` anywhere for old rows. If a future pass wants existing RFPs to actively carry an explicit `'preferred'` tag (rather than just falling back to the legacy UI), that needs a deliberate, reviewed one-off script against the two known JSONB locations - not a blind migration.
- **Compliance matrix cannot-meet reason text is not yet visible in compare/detail view** (see #5) - the column exists after 071, the write path saves it, but the two read surfaces' explicit column-select lists were deliberately not touched tonight (adding a column that doesn't exist yet to a live `.select()` would 500 the bid list page immediately, which is exactly the kind of pre-migration breakage this run was told to avoid). This is a real, working-but-incomplete state, logged as an open item rather than either skipped entirely or shipped unsafely.
